# Lulu Agent 当前状态与改进需求

日期：2026-09-07。本文是修复前的现状快照，可直接交给 Claude 做独立方案审查。

## 产品目标与约束
Lulu 面向普通 Windows 办公用户，是透明桌宠加独立工作窗口的本机助理。长期记忆必须具备。希望低配电脑也能使用，不要求用户自行安装模型、Python、Node 或配置开发环境。模型推理和个人数据处理优先完全本地；网络搜索、天气、实时行情需要网络，不能把“本地推理”等同于“断网也能获取实时数据”。复杂任务可靠性是目标，目前没有证明已经达成。

演示层已由用户认可，本轮不再调整动作或外观。当前窗口有对话、长期记忆、文件、任务、提醒、陪伴页面，以及所有页面底部固定输入区。

## 当前实现
- 执行底座：官方 DeepSeek Harness，固定源码版本 d347e703908d0406b7a7ef80e3a0e594d86b2215，sdk-minimal profile，Lulu 插件注册工具并检查执行产物。
- 模型：Ollama / Qwen2.5:7b，当前本机推理。Harness 本身不是模型，不会自动提升7B模型的规划或理解能力。
- 后端：Python、aiohttp；Harness 使用 Node 运行。窗口与桌宠使用 Godot。
- 数据：SQLite 保存记忆、会话、任务、执行事件和提醒；文件位于用户工作目录。记忆采用结构化记录与检索，没有独立向量服务和后台大模型。
- 上下文：最近对话按预算截取，保留近期任务目标、检查点与真实文件产物；续办可以读取旧任务上下文。
- 工具：读写修改文档、DOCX/PDF/TXT/MD生成及转换、CSV/XLSX统计、文件搜索、网页搜索与抓取、长期记忆增删查、提醒、任务检查点及续办。
- 文件安全：限制工作目录路径；部分修改自动备份；生成后读取验证正文、记录哈希与产物回执，不能只凭模型口头承诺算成功。
- 运行保障：本机令牌鉴权、单任务约束、超时、取消、进程监控及重启。当前错误提示和恢复交互仍不完整。
- 当前Mac应用包含模型、Ollama、Python、Node、Godot与Harness；约8.1GB应用、6.3GB压缩包。没有完成原生低配Windows部署/性能/稳定性验收，不能用Linux或Mac测试替代。

## 用户发现的两次失败
### 1. 澄清问题被当成文档正文交付
请求：“帮我生成一份btc今日各平台价格的word”。实际生成DOCX，内容却是“需要获取实时价格”“请提供平台”“待确认”等向用户提问的文字。聊天还宣称已经生成价格文档。

从代码可确认：generate_document 调用独立正文撰写器，撰写提示里包含“没有来源的事项明确写待确认”；返回的普通字符串经过长度/截断检查就进入文件写入。文件可读与内容一致检查只能证明写入成功，不能证明这是一份完成了用户目标的报告。没有结构化的“可交付正文 / 需要补充信息 / 无法完成”分支。

### 2. 提示查看执行记录，却没有对应入口
请求：“生成今日币安的btc价格走势的word”。聊天显示执行中断并要求查看执行记录后继续。当前桌面任务页只有查看结果与继续任务，没有把后端已存在的 /api/tasks/{id} 事件记录接口展示出来。用户既不知道失败原因，也无法针对原因补充信息。

截图只能确认上述现象；第二个任务的具体中断原因还需要结合实际事件日志核对，不能预先归因于没有确认窗口。

## 修复要求
1. 增加持久的待用户补充/确认状态。必要问题在窗口里提出，不写入交付文件，不显示已完成。
2. 用户回复后能继续原任务，携带原目标、澄清问题、用户答复、已完成步骤与真实产物；重启后仍可回答；避免重复生成、重复执行。
3. 区分“缺少完成任务必需的信息”和“任务已有充分授权”。不要让每次普通生成都弹确认窗口。默认值可合理确定时说明采用的口径；不可获取的实时事实不能靠用户确认伪装成已获取。
4. 把正文和控制信息分开。撰写器需要结构化结果，写入前做内容验收；拦住“请提供/请确认/我无法访问网络”等伪正文，同时避免误伤用户明确要求的问卷、确认函、待办清单。
5. 实时数据请求必须取得可用来源与时间戳，或明确暂停说明缺少数据。联网失败、搜索无结果、API受限和模型能力不足要分别说明。用户可选择上传真实资料，或明确改为模板/示例；未经选择不能交付空壳。
6. 提供执行记录入口：对话旁可查看本轮步骤，任务页可看历史步骤、错误、真实产物与等待中的问题。使用普通人能读懂的摘要；技术细节可展开，避免泄露本地鉴权令牌。
7. 完成标准：数据/信息满足目标、实际文件生成且可读、内容通过验收，才显示完成及桌宠“搞定”。中断、待补充、取消要有不同状态与明确下一步。
8. 补足基于失败案例的回归：缺少实时数据、正文返回澄清、拒绝/占位文字、用户回答后续办、重启恢复、重复确认、正常问卷/确认函、普通可直接完成的文档、记录入口与按钮可用性。

## 希望 Claude 审查的问题
- 在小模型+本地Harness约束下，如何设计计划、证据、澄清、执行、验收的状态机？哪些判断应由程序保障，哪些交给模型？
- 怎样设计正文撰写器的结构化协议及校验，减少控制文字混入文件，同时避免关键词拦截过度？
- 如何实现持久的用户问答与可靠恢复，而不是在HTTP请求里一直等用户？
- 对实时行情这类任务，是通用搜索足够，还是需要有限的明确数据适配器？如何保留来源、时间、币种、交易对与失败原因？
- 在不更换模型、不依赖云端推理的前提下，哪些能力可以承诺，哪些应明确限制？如何设计低配Windows实际验收？
